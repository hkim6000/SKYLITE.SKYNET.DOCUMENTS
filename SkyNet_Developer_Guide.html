Overview

SkyNet is a server-driven web framework for ASP.NET Core / .NET 10 and SQL Server, with vanilla JavaScript on the client — no SPA, no build step, no toolchain.

What SkyNet is

SkyNet is a middleware layer that sits between the ASP.NET Core pipeline and your application code. You write page classes in C#; the framework routes requests to them by class name, renders their HTML on the first request, and thereafter lets each method push surgical DOM mutations back to the browser.

The runtime consists of one assembly (SkyNet.dll) plus one client script (skynet.core.js) that the framework injects automatically. There is nothing to install on the client, nothing to compile on the front end, and no package manifest to maintain.

LayerTechnology
RuntimeASP.NET Core / .NET 10 — any OS the runtime supports
Web serverWhatever hosts ASP.NET Core: IIS, Kestrel behind nginx, a container
MiddlewareSkyNet (WebPage, ApiResponse, WebCore, SQLData, …)
DataSQL Server, reached through SQLData with SqlParameter
ClientVanilla JavaScript, skynet.core.js, plain CSS
BuildNone. dotnet build and copy.

The core idea

An interaction never returns a new HTML page. The browser POSTs to a page method; the method returns a JSON list of DOM operations; a small client engine applies them in place.

{ "data": [ { "o": 20, "k": "result", "p1": "<b>Saved</b>", "p2": "" } ] }

That single object says: opcode 20 (set innerHTML), on the element with id result, to the markup in p1. The server never hands back a page and the client never decides what the page should look like. The server owns the DOM and pushes changes to it.

You never write that JSON by hand. You call builder methods on an ApiResponse object and the framework serializes the ops for you:

C#
public async Task<ApiResponse> Save()
{
    ApiResponse response = new ApiResponse();
    response.SetElementContents("result", "<b>Saved</b>");
    return response;
}

This is the same family of idea as Hotwire Turbo Streams, Phoenix LiveView, and htmx — the server decides, the client applies. SkyNet arrived at it independently and implements it with no dependencies beyond the .NET runtime.

What it is not

  • Not an SPA framework. There is no client-side router, no virtual DOM, no component tree, no client state store.
  • Not a templating engine. There is no Razor, no view models bound to markup. HTML lives in .html files with {placeholder} tokens that the page class replaces, or is built server-side with string composition or ToolKit.
  • Not an ORM. You write SQL. SQLData parameterizes and executes it; DataTableListT<T> maps results onto plain classes when you want typed rows.
  • Not convention-over-configuration in the MVC sense. Routing is by class name resolved from the assembly, not by route table or attribute.

Why it suits AI-assisted development

SkyNet was shaped by, and for, a workflow in which a developer owns the architecture and database schema while an AI assistant generates most of the implementation. Several of its design choices are unusual in a hand-written codebase but are exactly what makes machine-generated code reliable here.

Everything a change needs is in one place. A page is four co-located files sharing one base name. There is no inheritance chain to trace, no dependency graph to resolve, no shared mixin whose behaviour changes under you. An assistant given one page has the complete context for that page.

  • Deliberate duplication over shared abstraction. Copying a block into a second page is preferred to extracting a helper. Abstraction saves keystrokes, which is the scarce resource for a human and the abundant one for an assistant; what it costs is locality, which is the scarce resource for both. A change to one page cannot break another.
  • No build step, so no build-time failure modes. Generated code either compiles or does not. There is no bundler config, no transpile target, no module resolution to get wrong.
  • Naming is the contract. Method names, element ids, CSS prefixes and placeholder tokens are all plain strings with a stated convention. An assistant can satisfy a convention stated in prose far more reliably than it can infer one from a framework's internals.
  • The whole client API is flat and prefixed. Every client global begins with $. There is no import to resolve and no namespace to guess.
  • Copy, retarget, adapt. Because pages do not share code, an existing page is a working template for the next one. "Build the Invoice page the way the Contact page works" is a complete and unambiguous instruction.

The trade-off is real. Strings crossing the C# / JS boundary — ExecuteScript("PageJs.onSaved();"), element ids, placeholder tokens — are not checked by any compiler. Rename a JS function and the C# that calls it fails silently at runtime. Duplication also means a bug fixed in one page stays broken in its six copies. Both are manageable, but only deliberately: see Verification checklist.

Request Lifecycle

Two paths, and only two. A GET builds and returns a whole document. Every interaction after that is a POST that returns DOM operations.

The two request paths. Shaded boxes are server-side; dark boxes are what the browser ends up with.

The GET render

A browser requests a page by name. SkyNet resolves the class from the executing assembly, instantiates it, runs the lifecycle hooks, and returns one complete HTML document.

  1. Construct. The page class constructor runs. This is where Translation is switched on and the page dictionary is loaded (see Translation).
  2. OnInit(type, func). Authentication and authorization. Returning a non-empty string stops the request with that message.
  3. OnLoad(). Optional early hook.
  4. OnInitialized(). The main body. Load data, build HTML fragments, replace {placeholder} tokens in HtmlDoc.HtmlBodyText, queue HtmlDoc.InitialScripts.
  5. OnBeforeRender(). Last chance to alter the document.
  6. Render. The framework assembles <head> and <body>, injects skynet.core.js, and auto-loads the page's own .js and .css by name.
  7. OnAfterRender(). Post-processing on the finished document — this is where translation is applied.

Assets load by convention. Requesting page Contact loads scripts/Contact.js and styles/Contact.css automatically. You only call HtmlDoc.AddJsFile() / AddCSSFile() for additional files.

The POST round trip

After the document is loaded, every interaction is an XHR POST that returns operations rather than markup.

  1. A handler calls $ApiRequest('Save', data) (or $('Save'), or $Call('Save', 'k=v')).
  2. The client builds FormData, appending the payload plus the standard envelope — timezone, URL params, page-scoped localStorage, and every form field on screen. See the POST envelope.
  3. It POSTs to a URI derived from the current path: <area>/<Page>/<Method>.
  4. Server-side, OnInit authenticates, then the named method runs and returns an ApiResponse.
  5. OnResponse(apiResponse) gets a final pass at the op list.
  6. The response body is { "data": [ {o,k,p1,p2}, … ] }.
  7. $ApiRequestSuccess parses it and $WebAct applies each op in order.

Why this shape helps. Because the whole envelope is sent on every call, a server method can read any on-screen field with GetDataValue("fieldId") without that field being named in the payload. Generated client code does not have to enumerate the form — it only sends what is specific to the action.

Hard navigation

If a response body begins with <!DOCTYPE html>, the client does not try to parse it as operations. It calls document.write(body) and replaces the page wholesale.

function $ApiRequestSuccess(args){ if(args.indexOf("<!DOCTYPE html>") != -1){ document.write(args) } else { $WaitOff(); $WebAct(JSON.parse(args)) } }

This is the escape hatch used for session-expiry redirects and login hand-offs, where the server decides mid-request that the user should be looking at a different document entirely.

Error surfacing. If the response is neither a document nor valid JSON, the client writes the parse error and the raw body into document.body. An unhandled server exception therefore replaces the page with its own text — useful in development, and a reason to keep customErrors/exception pages configured in production.

Page Anatomy

A page is four co-located files sharing one base name. Nothing outside those four files is required to understand it, and nothing inside them is shared with another page.

The four files

FileHolds
codes/…/Contact.csThe page class (: WebPage), its server methods, and any DTOs it needs
htmls/Contact.htmlMarkup with {placeholder} tokens the class replaces
scripts/Contact.jsOne IIFE assigned to ContactJs
styles/Contact.cssStyles, every selector under one short page-unique prefix

The framework finds the last three by name. You write Contact.cs, request Contact, and the HTML, script and stylesheet are located and injected without registration.

Assets live in root folders — scripts/, styles/, images/, photos/, htmls/, data/ — not in wwwroot. The folder names come from application.cfg; see Configuration.

Self-contained, duplicate-don't-abstract

This is the single most important convention in a SkyNet codebase, and the one that most surprises developers arriving from layered architectures.

A page owns its own CSS prefix, its own JS namespace, and its own C# methods and DTOs. Prefer copying a block into a second page over introducing a shared helper. The only cross-page C# sharing is a *Model.cs file holding plain DTO or enum declarations.

What you gain

  • A page can be read, changed or deleted without touching anything else
  • No inheritance chain to trace, no shared helper whose behaviour shifts under you
  • An existing page is a complete, working template for the next one
  • Several pages can be open at once without CSS or JS collisions

What it costs

  • A bug fixed in one page stays broken in its copies
  • A convention change means N edits, not one
  • Total line count is higher than a DRY equivalent

The reasoning. Abstraction trades locality for keystrokes. Keystrokes are the scarce resource for a human author and the abundant one for an assistant; locality is scarce for both. When most implementation is generated, the version that is easiest to regenerate correctly — and safest to get wrong — is the one where the blast radius of any single file is exactly one page.

The JS namespace rule

A page script is REQUIRED to be a single IIFE assigned to <PageName>Js, exposing a small surface through its return object. Nothing else is declared at global scope.

Contact.js
var ContactJs = (function () {

    // private
    function val(id) { var e = document.getElementById(id); return e ? e.value : ''; }

    function save() {
        $WaitOn();
        $ApiRequest('Save', JSON.stringify([
            { key: 'name', vlu: val('cnt-name') }
        ]));
    }

    function onSaved(msg) { /* called by the server via ExecuteScript */ }

    function reveal() { /* wire events, set initial state */ }

    return {
        reveal:  function ()    { reveal(); },
        save:    function ()    { save(); },
        onSaved: function (m)   { onSaved(m); }
    };

})();

document.addEventListener('DOMContentLoaded', function () { ContactJs.reveal(); });

The exposed surface is typically reveal plus the event handlers that markup calls by name and the callbacks the server invokes by name. Anything the server or the HTML refers to must be on the return object; anything else stays private.

Partials initialise differently. A page injected as a partial arrives after DOMContentLoaded has already fired, so the listener above never runs. Partials call PageJs.reveal() directly at the end of the file, or the injecting page polls for the namespace. See Script timing.

Placeholders

The .html file is static markup containing tokens. The class replaces them in OnInitialized.

Contact.html
<div class="cnt-wrap">
  <h1 class="cnt-title">{plhd_title}</h1>
  <input class="cnt-input" id="cnt-name" value="{plhd_name}" />
  <div class="cnt-rows">{plhd_rows}</div>
</div>
Contact.cs
public override async Task OnInitialized()
{
    HtmlDoc.HtmlBodyText = HtmlDoc.HtmlBodyText
        .Replace("{plhd_title}", HtmlEncode(title))
        .Replace("{plhd_name}",  HtmlEncode(name))
        .Replace("{plhd_rows}",  await BuildRows());
}

Conventions worth keeping:

  • Prefix tokens {plhd_…} so they are greppable and never collide with CSS or translation syntax.
  • Replace every token you declare. An unreplaced token renders literally on the page.
  • HtmlEncode any value that came from the database or the user. The replacement is a raw string splice — nothing escapes it for you.

Models and DTOs

A page keeps its own DTOs in its own file. When two pages in the same area genuinely need the same shape, it goes in that area's single Models/<Area>Model.cs — declarations only, no behaviour.

codes/Areas/Sales/Sales_Order.cs ← page class + its own DTOs codes/Areas/Sales/Sales_Invoice.cs ← page class + its own DTOs codes/Areas/Sales/Models/SalesModel.cs ← shared DTOs / enums, no logic

If a type is used by one page, put it in that page's file. Promoting it to the area model is a deliberate decision, not a default.

WebPage Class

Every page derives from SkyNet.WebPage. It supplies the document, the lifecycle hooks, the translation surface, and — because it extends WebCore — the entire server utility API unqualified.

Declaring a page

C#
using SkyNet;

namespace MyApp.codes
{
    public class Contact : WebPage
    {
        public override async Task OnInitialized()
        {
            HtmlDoc.SetTitle("Contact");
            HtmlDoc.HtmlBodyText = HtmlDoc.HtmlBodyText.Replace("{plhd_name}", HtmlEncode(name));
        }

        public async Task<ApiResponse> Save()
        {
            ApiResponse response = new ApiResponse();
            // ... work ...
            response.ExecuteScript("ContactJs.onSaved();");
            return response;
        }
    }
}

There is no attribute, no registration, no route entry. The framework resolves Contact from the executing assembly by class name.

Routing is by class name, not by path. $Navigate('Contact') and $ApiRequest('Contact/Save') both resolve through the assembly. The folder a class sits in — including an Areas/ subfolder — does not appear in the call. Class names must therefore be unique across the whole assembly.

The app base-class pattern

Products built on SkyNet normally insert one application-wide base class between WebPage and every page, to hold concerns that genuinely are global: authentication, translation, run-mode checks.

Shared/WebBase.cs
public class WebBase : WebPage
{
    public override async Task<string> OnInit(string type, string method)
    {
        AuthData? auth = Helper.GetAuthData();
        if (auth == null)
            return "Your session has expired. Please sign in again.";

        return string.Empty;   // empty = proceed
    }
}

Pages then derive from WebBase instead of WebPage. Pre-authentication pages — sign-in, sign-up, password reset — derive from WebPage directly so the gate does not lock them out.

This is the one sanctioned exception to duplicate-don't-abstract. It exists because an authentication check that is copied into every page is a check that will eventually be missed in one. Keep the base class small and restricted to cross-cutting policy; resist adding page helpers to it.

Partial pages

PartialDocument("Detail") runs another page's full GET lifecycle and hands you its HtmlDocument instead of writing it to the response. Pair it with SetElementContents to swap a region of the current page:

C#
public async Task<ApiResponse> OpenArea()
{
    string t = GetDataValue("t");   // target element id
    string p = GetDataValue("p");   // page class name

    HtmlDocument htmlDoc = await PartialDocument(p);
    ApiResponse response = new ApiResponse();
    response.SetElementContents(t, htmlDoc);
    return response;
}

This is the mechanism behind shell-plus-content layouts, tab strips and drill-in overlays. It is covered in full in Areas & Partials.

Body text and placeholders

The framework loads htmls/<Page>.html into HtmlBodyText before OnInitialized runs. Your job is to replace the tokens:

C#
HtmlDoc.HtmlBodyText = HtmlDoc.HtmlBodyText
    .Replace("{plhd_title}",  HtmlEncode(title))
    .Replace("{plhd_count}",  count.ToString())
    .Replace("{plhd_rows}",   rowsHtml);

Replacement is a raw splice. Nothing is escaped for you. Run every value that came from the database, the query string or a user through HtmlEncode before it goes in. The only values that legitimately skip it are HTML fragments you built yourself — and those must have encoded their own inputs.

InitialScripts

HtmlDoc.InitialScripts is an ApiResponse whose operations run when the document loads. It is how the server hands the page its starting state without embedding a script block in the markup.

C#
HtmlDoc.InitialScripts.SetVariableData("ContactText", new
{
    btn_save   = "{!Save Changes!}",
    saving     = "{!Saving…!}",
    err_name   = "{!Please enter a name.!}"
}, HtmlTranslator);

HtmlDoc.InitialScripts.Navigate("Login");   // or bail out entirely

Every ApiResponse method is available on it — SetElementContents, StoreLocalValue, SetCookie, ExecuteScript, Navigate. It is the natural place to redirect an unauthenticated visitor during OnInitialized.

InitialScripts are deferred. They execute after the page script file has been evaluated, not before. Page JS must therefore not read $GetVarData() at load time — the data is not there yet. Read it lazily, at the moment of first use. See When it arrives.

Content Security Policy

A CSP header is emitted by default. Inline script pushed through opcode 80 is nonce-wrapped so it passes, but third-party script from another origin does not.

HtmlDoc.ContentSecurityPolicy = false; // only when a page must load external script

Switch it off for the single page that needs it, never application-wide.

Building without a template

A page is not obliged to have an .html file. You can compose the body entirely in C# — with string building, or with ToolKit:

C#
HtmlTag h = new HtmlTag(HtmlTags.h3);
h.InnerText = "Hello";
HtmlDoc.HtmlBodyText = h.HtmlText;

The template approach is preferred for anything a person will design or restyle; server-side building earns its place for markup that is genuinely data-shaped, such as a grid whose columns come from configuration.

ApiResponse

The command container. Every server method invoked from the client returns one. You populate it with builder calls; the framework serializes them into the op list the browser applies.

The model

ApiResponse is not a data envelope — it carries no payload for the client to interpret. It carries instructions, executed in the order you added them.

C#
public async Task<ApiResponse> ProcessForm()
{
    ApiResponse response = new ApiResponse();          // 1. instantiate

    response.SetElementContents("statusMessage", "Processing complete.");
    response.SetElementStyle("submitButton", "display", "none");   // 2. populate
    response.Navigate("ConfirmationPage");

    return response;                                     // 3. return
}

Think in instructions, not payloads. The commonest mistake when generating SkyNet code is to return data and expect client JS to render it. There is no render step on the client. If the browser should show something different, the server says exactly which element changes and to what.

The (data, emsg) idiom

Reads return a tuple: the data, and an error string that is empty on success. Nothing throws for an ordinary SQL failure. Check the string.

var (dt, emsg) = await Helper.GetDataTable(sql, parms);

    response.ModalWindow("Issue Found", Helper.ErrContentHtml(emsg));

Three states, not two. Success-with-rows, success-with-no-rows, and failure are distinct and each needs its own branch. Generated code that tests only dt.Rows.Count > 0 silently swallows connection failures and SQL syntax errors, which then present as "the page is just empty".

Parameterization

REQUIRED Every value that reaches SQL goes through a SqlParameter. Concatenating user input into a query string is the one thing this framework gives you no protection against.

C#
var parameters = new List<SqlParameter>
{
    new SqlParameter("userid", SqlDbType.NVarChar) { Size = 50,  Value = userId },
    new SqlParameter("email",  SqlDbType.NVarChar) { Size = 200, Value = email  },
    new SqlParameter("amount", SqlDbType.Decimal)                { Value = amount }
};

string sql = @"SELECT ACCT_ID, ACCT_NAME
                 FROM ACCT
                WHERE USER_ID = @userid AND ACCT_NAME LIKE @email";

Note the parameter name is given without the @ in the constructor and with it in the SQL. Always set Size on string parameters — omitting it lets ADO.NET infer a size from the current value, which defeats plan reuse.

Identifiers cannot be parameterized. A dynamic sort column or table name has to be composed, so validate it against a whitelist you control rather than passing it through.

Batch writes

PutDataAsync takes a list of statements sharing one parameter list, executed together. This is how multi-table operations stay consistent.

C#
var sqls = new List<string>
{
    @"INSERT INTO ACCT (ACCT_ID, USER_ID, ACCT_NAME, SYSDTE)
      VALUES (@acctid, @userid, @acctname, GETDATE())",

    @"INSERT INTO ACCTLOG (LOG_ID, ACCT_ID, LOG_MEMO, SYSDTE)
      VALUES (UPPER(CONVERT(NVARCHAR(50), NEWID())), @acctid, N'Opening', GETDATE())"
};

var parms = new List<SqlParameter>
{
    new SqlParameter("acctid",   SqlDbType.NVarChar) { Size = 50,  Value = acctId },
    new SqlParameter("userid",   SqlDbType.NVarChar) { Size = 50,  Value = userId },

One parameter list for all statements. Every statement in the batch sees every parameter, so names must be unique across the whole batch and each must be supplied exactly once. This is the most common cause of a batch failing with "must declare the scalar variable".

The Helper pattern

Products wrap SQLData in an application Helper class that adds cross-cutting behaviour to every call. This is the layer where audit logging and read-only mode live.

Shared/Helper.cs — the shape
public static async Task<(DataTable dt, string emsg)> GetDataTable(
    string sSql, List<SqlParameter>? parameters = null)
{
    SQLData msql = new SQLData();
    return await msql.GetDataAsync(sSql, parameters);
}

public async Task<string> PutData(List<string> sSql, List<SqlParameter>? parameters = null)
{
    if (await AppRunMode() == 2)
        return "The requested process is currently locked in archive mode.";

    sSql.AddRange(SqlLogSql(sSql, parameters));   // append audit INSERTs

    SQLData msql = new SQLData();
    return await msql.PutDataAsync(sSql, parameters);
}

Two behaviours worth copying:

  • Archive mode blocks writes. When the application's run mode is 2, PutData refuses before touching the database. See Run mode.
  • Every write is audited. The helper appends an INSERT into an audit table capturing the calling area, class and method (via [CallerMemberName]), the user, the IP, the SQL and the parameters — in the same batch, so the audit row cannot be lost if the write succeeds.

Auditing captures parameter values. That includes anything you pass — encrypted passwords, tokens, personal data. Either exclude sensitive statements from the audited path or redact before logging. The low-level new SQLData().PutDataAsync(...) bypasses both the audit and the archive lock; use it deliberately, not by accident.

Naming discipline

Two mechanisms in the engine read function names at runtime:

function $fn(args) { return args.callee.toString().match(/function ([^\(]+)/)[1] } function $fnr(args) { return args.callee.caller.toString().match(/function ([^\(]+)/)[1] }

These let a handler call its server-side namesake without repeating it:

Contact.js
function saveProfile() {
    $ApiRequest();                      // → calls Contact.saveProfile() on the server
}

Three constraints follow, and all three are easy to violate by accident:

1. Never mangle identifiers when minifying. The engine reads the function's own source text to find its name. A minifier that renames saveProfile to a will send the request to a server method called a.

2. Never convert to arrow functions. The regex requires the literal token function followed by a name. An arrow function or an anonymous expression has neither.

3. The bare form does not work in strict mode. arguments.callee throws a TypeError under "use strict". If a page script opts into strict mode, every call must name its target explicitly — $ApiRequest('saveProfile', data).

Prefer the explicit form. $ApiRequest('Save', data) costs six characters and removes all three hazards at once. The implicit form is elegant to read and fragile to generate: it depends on the calling function's name matching a server method exactly, which is invisible at the call site and silently wrong when it drifts.

Error handling

function $ApiRequestError(args){ $WaitOff(); alert($localValue(args) == "" ? args : $localValue(args)) }

The default error callback shows an alert, first checking whether the message is a localStorage key it should translate. Pass your own fourth argument to $ApiRequest to replace it.

Transport errors only. This callback fires when the XHR itself throws. A server method that returns an ApiResponse describing a failure is, to the transport, a success — which is why error handling in SkyNet is normally an op the server queues (ExecuteScript into a page callback, or ModalWindow), not a client-side rejection path.

Do not modify the engine

skynet.core.js is framework-supplied and shared by every application on the framework. Page behaviour belongs in the page's own IIFE; cross-page behaviour belongs in your own script file added with HtmlDoc.AddJsFile. Editing the engine forks it from every other product on SkyNet and makes upgrades a merge.

URI resolution

The target is turned into a URL relative to the current path, not to the site root:

contains "http" → used as-is contains "/" → one level up from $appPath(), then + target otherwise → $appPath() + "/" + target

$appPath() keeps the first two path segments of the current location. The practical consequence is that 'Save' targets the current page and 'OtherPage/Save' targets a sibling — the folder a class lives in never appears, because routing is by class name.

How form values are collected

  • Keyed by id || name — id wins for most inputs, name wins for checkboxes and radios.
  • Checkboxes and radios are sent only when checked, carrying their value, or "1" when the value is empty or "on".
  • file inputs append their File objects, so uploads need no special handling.
  • select, textarea and button send their value.

This is the framework's biggest labour-saver. A server method can read any field on screen with GetDataValue("cnt-email") without the client naming it. Client code should send only what is specific to the action — a row id, a mode flag — and let the envelope carry the form. Enumerating every field into the payload is redundant work and a second place for names to drift.

An unchecked checkbox sends nothing at all. GetDataValue("agree") returns empty both when the box is unchecked and when it does not exist. If the difference matters, pair it with a hidden input, or send an explicit flag in the payload.

Everything on screen goes out on every call. A hidden field holding a token or a decrypted value is transmitted with each request, including calls that have nothing to do with it. Keep secrets out of the DOM.

Response handling

function $ApiRequestSuccess(args){ if (args.indexOf("<!DOCTYPE html>") != -1) { document.write(args) } else { $WaitOff(); if (args == null || args == "") return; try { $WebAct(JSON.parse(args)) } catch (err) { document.body.innerHTML = err.message + " : " + args } } }

Reading ops while debugging

When a server call "does nothing", the op list tells you which of three things happened. Open the network tab and look at the response body.

What you seeWhat it means
{"data":[]}The method ran and queued nothing. Your branch returned early.
Ops present, nothing changesThe target does not exist. Check the id, and check whether it lives inside an element that was replaced earlier in the same list.
Ops stop part-wayAn op threw. Opcode 80 running bad JS, or a broken handler (above).
HTML in the bodyAn unhandled server exception, or the hard-navigation path.

Order matters and is easy to get wrong. Ops apply top to bottom against a live DOM. If op 3 replaces a container and op 5 targets an element that was inside it, op 5 silently finds nothing. Queue the inner updates before the outer replacement, or rebuild the whole region in one op.

Client Storage

Three stores, three scoping rules, and one behaviour that surprises everyone: page-scoped localStorage is transmitted to the server on every request.

localStorage namespacing

The page prefix is derived from the current URL — the last path segment, minus any extension. A key containing #global. anywhere is left untouched.

From the server

Storage is transmitted on every request

This is the part that catches people. $getLocalData runs on every $ApiRequest and appends storage to the outgoing FormData:

function $getLocalData(f){ var h = location.href.split("/").pop().split(".")[0] + "."; for (var i = 0; i < localStorage.length; i++){ var key = localStorage.key(i); if (key.indexOf("#global.") != -1) f.append(key, localStorage.getItem(key)); else if (key.indexOf(h) != -1) f.append(key.replace(h, ""), localStorage.getItem(key)); } }

So a value stored under filter arrives server-side as GetDataValue("filter"), with the page prefix stripped. Global keys arrive under their full #global. name.

This is a feature, used deliberately. Store a grid's current filter, sort column and page number in page-scoped storage and every subsequent call carries them automatically — the client never has to assemble them into a payload, and the state survives a full page reload. It is the framework's idiomatic answer to "where does view state live".

Two consequences to plan around.

1. A storage key can shadow a form field. Both land in the same FormData under the same name. If localStorage holds status and the page also has an input with id="status", the server sees two values for one key and which one wins is not something to rely on. Namespace your storage keys — cnt_status rather than status.

2. Never store anything sensitive. It is readable by any script on the origin, it survives the session, and it is retransmitted on every single request.

CS → JS Data Transfer

The supported way to hand structured data to a page's JavaScript. One call on the server, one call on the client, no inline JSON blob in the markup.

The two calls

// server public void SetVariableData<T>(string name, T obj, Translator? HtmlTranslator = null) // client var v = $GetVarData(name); // returns the value and DELETES it var v = $GetVarData(name, false); // returns it and keeps it
Contact.cs
HtmlDoc.InitialScripts.SetVariableData("ContactText", new
{
    btn_save    = "Save Changes",
    saving      = "Saving…",
    err_name    = "Please enter a name.",
    err_generic = "Something went wrong. Please try again."
});
Contact.js
var data = $GetVarData('ContactText');
var label = data.btn_save;

An anonymous object is the usual argument; a declared class works identically. The property names become the JavaScript keys verbatim.

The wire format

The object is serialized to JSON, UTF-8 encoded, base64'd, and delivered as a call to $SetVarData. The client decodes it into a single global store:

window.$VarData = window.$VarData || {}; function $SetVarData(name, b64){ try { $VarData[name] = b64 ? JSON.parse(decodeURIComponent(escape(atob(b64)))) : null } catch (e) { $VarData[name] = null } }

Two things follow from this that matter in practice.

1. A decode failure is silent. The catch stores null. If the payload does not survive the round trip, $GetVarData returns null and your page reads properties off nothing. Guard the read: var t = $GetVarData('X') || {};

2. The content is opaque to any text pass. Because the payload is base64 by the time it reaches the document, nothing that scans the HTML can see inside it — including the translator. That is why SetVariableData takes a translator as its third argument; see below.

When it arrives

Values queued in HtmlDoc.InitialScripts execute after the page's script file has been evaluated. At the moment Contact.js is parsed and its DOMContentLoaded handler runs, $VarData is still empty.

skynet.core.js → loaded styles/Contact.css → loaded scripts/Contact.js → loaded and evaluated ← $VarData is EMPTY here InitialScripts ops → executed ← $VarData is populated here

Do not read variable data at load time. This is the single most common mistake with the mechanism:

// WRONG — runs before the data has arrived var TXT = $GetVarData('ContactText') || {}; function reveal(){ setText(btn, TXT.btn_save); } // always empty

The lazy-read pattern

Read at first use, and cache only once the data is actually there:

Contact.js
var TXT = null;
function t(k) {
    if (!TXT) { TXT = $GetVarData('ContactText'); }
    return (TXT && TXT[k]) ? TXT[k] : '';
}

If the first call happens too early, TXT stays falsy and the next call retries. No timing assumption, no polling, no ordering requirement.

Use this pattern by default. It is correct whether the page was loaded normally or injected as a partial, whether the data arrived before or after the script, and whether $GetVarData deletes on read or not. Generated code that caches at load time works in one of those situations and fails silently in the rest.

Delete-on-read

function $GetVarData(name, remove){ var v = $VarData[name]; if (remove !== false) delete $VarData[name]; return v; }

The default is to remove. Two reads of the same name return the value and then undefined. Either cache the first result — as the lazy pattern does — or pass false explicitly.

Translated payloads

Pass the page's HtmlTranslator as the third argument and {!…!} tokens in the values are resolved before encoding:

Contact.cs
HtmlDoc.InitialScripts.SetVariableData("ContactText", new
{
    btn_save = "{!Save Changes!}",
    saving   = "{!Saving…!}",
    err_name = "{!Please enter a name.!}"
}, HtmlTranslator);

This is REQUIRED for any user-visible text the client writes into the DOM. Without the third argument the tokens travel to the browser literally and the user sees {!Save Changes!} on a button.

Translation

Mark text with {!…!}, store the wording in a database table, and the framework substitutes it on the way out. Copy becomes data — editable without a deploy, in any number of languages.

The token

private const string Prefix = "{!"; private const string Suffix = "!}";

Wrap any visible string in the markup:

Contact.html
<h1 class="cnt-title">{!Welcome back!}</h1>
<label class="cnt-label">{!Email!}</label>
<input placeholder="{!you@example.com!}" />
<button>{!Sign In!}</button>

The key is the English text itself. There is no separate identifier to invent, keep in sync, or look up. A missing dictionary row leaves the literal text on screen — so an untranslated page degrades to readable English rather than to label.login.title.

Why text-as-key matters here. Symbolic keys require a second artefact and a naming convention, and they fail visibly when they drift. Text-as-key means marking a string is a purely local edit: wrap it, and you are done. It is the cheapest possible instruction to give — "wrap every visible label in {!…!}" — and it cannot go wrong in a way that produces the wrong words.

Enabling it on a page

Contact.cs
public Contact()
{
    Translation = true;

    string pageName = this.GetType().ToString().Split('.').LastOrDefault() ?? this.GetType().Name;
    var pageDict = Helper.GetPageDict(pageName).GetAwaiter().GetResult();
    if (pageDict != null && pageDict.Count > 0) HtmlTranslator.Add(pageDict);
}
  • Translation = true activates the translator, driven by the browser's language.
  • HtmlTranslator.Add(…) loads this page's dictionary rows, which take priority over anything the translator would otherwise produce.

Both belong in the constructor, because the dictionary must be present before any rendering or response building happens.

Use the short class name as the dictionary target. GetType().ToString() returns the namespace-qualified name (MyApp.codes.Areas.Sales.Contact); splitting on . and taking the last segment gives Contact, which is what the table stores.

When substitution happens

Translation runs on the finished HTML document, immediately before it is sent — in OnAfterRender, after every placeholder replacement and every fragment you built.

OnInitialized build fragments, replace {plhd_*} ← tokens still literal OnBeforeRender final adjustments ← tokens still literal [render] assemble the document OnAfterRender translate ← {!...!} resolved here → sent to the browser

Three useful consequences:

  • Tokens survive everything upstream — you can place them inside attributes, inside strings you concatenate in C#, inside fragments built row by row.
  • Placement next to a {plhd_*} placeholder is safe: {plhd_appname} {!is currently unavailable.!}
  • It is server-side and has nothing to do with client JavaScript.

Wildcards

  • TARGET = '*' — applies to every page. Use for genuinely universal words: Save, Cancel, Delete.
  • ISOCODE = '*' — applies to every locale.
  • A page-specific row wins over a '*' row.

The lookup

The standard loader resolves the locale with a fallback chain and returns rows for the page plus the wildcards:

Helper.cs
public static async Task<List<Translator.DictionaryEntry>> GetPageDict(
    string pagename, string clientLanguage = "")
{
    string lang = clientLanguage;
    if (string.IsNullOrEmpty(lang)) lang = new WebCore().ClientLanguage ?? string.Empty;
    if (string.IsNullOrEmpty(lang)) lang = "en-US";

    string sSql = @"IF EXISTS (SELECT * FROM XYSDICT WHERE ISOCODE = @isocode)
       BEGIN
           SELECT TARGET, ISOCODE, KEYWORD, TRANSLATED FROM XYSDICT
            WHERE (TARGET = @pageid OR TARGET = N'*')
              AND (ISOCODE = N'*' OR ISOCODE = @isocode)
            ORDER BY KEYWORD
       END
       ELSE
       BEGIN
           SELECT TARGET, ISOCODE, KEYWORD, TRANSLATED FROM XYSDICT
            WHERE (TARGET = @pageid OR TARGET = N'*')
              AND (ISOCODE = N'*' OR ISOCODE = N'en-US')
            ORDER BY KEYWORD
       END";

    // ... parameters, execute, map rows to Translator.DictionaryEntry ...
}

If the requested locale has no rows at all, the query falls back to en-US — so adding a language is purely additive and a partially translated language degrades per-string rather than failing wholesale.

Working practice

  1. Write the page in plain English.
  2. Wrap every visible string in {!…!} — text nodes and placeholder attributes.
  3. Move any user-visible JS literal into a SetVariableData payload, tokens and all.
  4. Extract the distinct tokens and generate idempotent INSERTs for ISOCODE = 'en-US' with TRANSLATED = KEYWORD.
  5. Add other locales as rows whenever you are ready. No code changes.
IF NOT EXISTS (SELECT 1 FROM XYSDICT WHERE TARGET = N'Contact' AND ISOCODE = N'en-US' AND KEYWORD = N'Welcome back') INSERT INTO XYSDICT (TARGET, ISOCODE, KEYWORD, TRANSLATED) VALUES (N'Contact', N'en-US', N'Welcome back', N'Welcome back');

KEYWORD is nvarchar(100). A sentence longer than that cannot be a key. Split long copy into shorter tokens, or keep it out of the translated set deliberately.

Areas & Partial Pages

Areas organise code on disk. Partial pages let one page render another into a region of itself — the mechanism behind shells, tabs and drill-in panels.

Folder layout

Areas are a filing convention. They do not appear in URLs, in call targets or in class resolution.

codes/ Home.cs ← root-level page Shared/ WebBase.cs ← app base class Helper.cs ← app data/auth helper Models/ AppModels.cs ← app-wide DTOs Areas/ Sales/ Sales_Order.cs Sales_Invoice.cs Models/ SalesModel.cs ← area DTOs — declarations only User/ Login.cs SignUp.cs htmls/ Home.html Sales_Order.html Login.html ← flat, by page name scripts/ Home.js Sales_Order.js Login.js ← flat styles/ Home.css Sales_Order.css Login.css ← flat

The asset folders are flat. Class files nest by area; htmls/, scripts/ and styles/ do not. Every page name must therefore be unique across the whole application — which is also what class-name routing requires. The common convention is to prefix with the area: Sales_Order, Sales_Invoice.

Class-name routing

SkyNet resolves a page by looking up the class name in the executing assembly. The namespace and folder are irrelevant to the caller:

$Navigate('Sales_Order'); // not 'Areas/Sales/Sales_Order' $ApiRequest('Sales_Order/Save', data); // not 'Sales/Sales_Order/Save'

There is no route table to keep in step. Adding a page means adding four files; nothing registers it. The cost is that a duplicate class name is an application-level collision rather than a compile error in one project — so name pages for their area from the start.

PartialDocument

public async Task<HtmlDocument> PartialDocument(string typeName, string param = "") public async Task<string> PartialPage(string typeName, string param = "")

PartialDocument runs another page's full GET lifecycle — constructor, OnInit, OnInitialized, translation — and returns its HtmlDocument instead of writing it to the response. Hand that to SetElementContents and the region is replaced.

Home.cs — the generic opener
public async Task<ApiResponse> OpenArea()
{

    string p = GetDataValue("p");   // page class name

    HtmlDocument htmlDoc = await PartialDocument(p);
    ApiResponse response = new ApiResponse();
    response.SetElementContents(t, htmlDoc);
    return response;
}
Home.js
function go(page) {
    $WaitOn();
    $ApiRequest('Home/OpenArea', JSON.stringify([
        { key: 't', vlu: 'main-content' },
        { key: 'p', vlu: page }
    ]));
}

One method serves every menu item. The partial's own .js and .css are appended to the document as part of the injection.

The shell pattern

The usual arrangement: one page owns the chrome, every other page is content injected into it.

Home.html
<div class="hm-shell">
  <aside class="hm-side">
    <button data-page="Sales_Order">{!Orders!}</button>
    <button data-page="Sales_Invoice">{!Invoices!}</button>
  </aside>
  <main class="hm-main" id="main-content"></main>
</div>

What you gain

  • The chrome is written once, in one page
  • Switching areas does not reload the shell
  • Each content page stays four self-contained files

What you lose

  • The URL never changes — refresh returns to the shell's default
  • No deep links, no working Back button
  • The content page cannot own the document title

If linkability matters, use Navigate per page instead and let each page render its own chrome — at the cost of duplicating the shell markup into every page. Both are legitimate; choose once, per application.

Script timing

A partial arrives after DOMContentLoaded has already fired. The usual bootstrap therefore never runs:

document.addEventListener('DOMContentLoaded', function(){ DetailJs.reveal(); }); // never fires

Two ways out. Either have the partial start itself:

Detail.js — self-starting
var DetailJs = (function () { /* … */ })();

DetailJs.reveal();   // runs when the injected script is evaluated

Or have the injector wait for the namespace, which is the more robust option because script injection is asynchronous:

Home.cs
response.SetElementContents("main-content", htmlDoc);
response.ExecuteScript(
    "(function w(){ if(window.DetailJs){ DetailJs.reveal(); } else { setTimeout(w,30); } })();");

Prefer the polling form for anything that must run. The self-starting form depends on the injected script having been evaluated by the time the op list finishes — usually true, not guaranteed. The poll costs three lines and removes the race entirely.

Carrying state across an injection

Re-injecting a partial rebuilds it from scratch: which tab was open, which row was selected and any success message are all gone. Put the intent somewhere that survives, then restore on the way in.

Detail.js
function reload(pane) {
    try { sessionStorage.setItem('detail_pane', pane || 'main'); } catch (e) { }
    $WaitOn();
    $ApiRequest('Home/OpenArea', JSON.stringify([
        { key: 't', vlu: 'main-content' },
        { key: 'p', vlu: 'Detail' }
    ]));
}

function reveal() {
    var pane = 'main';
    try {
        pane = sessionStorage.getItem('detail_pane') || 'main';
        sessionStorage.removeItem('detail_pane');
    } catch (e) { }
    showPane(pane);
}

Reloading the partial after a write is often better than patching the DOM: the rows come back rendered, encoded and translated by the same server code that built them the first time, with no second code path to keep in step.

Authentication in partials

A partial runs its own OnInit, so it is gated like any other page. But a partial cannot usefully redirect — it is being rendered into a region, not returned as a document. Have it return empty content and let the injecting page handle the session check, or queue InitialScripts.Navigate("Login") from the shell.

Hosting

SkyNet is ordinary ASP.NET Core, so it runs anywhere the .NET 10 runtime does — Windows, Linux or macOS; behind IIS, behind nginx or Apache in front of Kestrel, in a container, or self-hosted. Nothing in the framework is tied to a particular web server.

What is distinctive is where static assets live. SkyNet serves them from the content-root folders named in application.cfg — scripts/, styles/, images/ — rather than from wwwroot.

The whole content root is reachable. That includes appConfig/, which holds the database password and the encryption key in plaintext, and codes/, htmls/, data/, logs/ and bin/. Blocking those paths is the first deployment task on any host, not a later hardening pass.

        private async Task<string> BuildRows(string userId)
        {
            var parms = new List<SqlParameter>
            {
                new SqlParameter("userid", SqlDbType.NVarChar) { Size = 50, Value = userId }
            };

            var (dt, emsg) = await Helper.GetDataTable(
                @"SELECT CONTACT_ID, NAME, EMAIL FROM CONTACT
                   WHERE USER_ID = @userid ORDER BY NAME", parms);

            if (!string.IsNullOrEmpty(emsg) || dt == null || dt.Rows.Count == 0)
                return "<div class=\"cnt-empty\">{!No contacts yet.!}</div>";

            StringBuilder sb = new StringBuilder();
            foreach (DataRow row in dt.Rows)
            {
                string id    = row["CONTACT_ID"]?.ToString() ?? string.Empty;
                string name  = row["NAME"]?.ToString()       ?? string.Empty;
                string email = row["EMAIL"]?.ToString()      ?? string.Empty;

                sb.Append("<div class=\"cnt-row\">");
                sb.Append("<div class=\"cnt-row-main\">");
                sb.Append("<div class=\"cnt-row-name\">" + HtmlEncode(name) + "</div>");
                sb.Append("<div class=\"cnt-row-sub\">"  + HtmlEncode(email) + "</div>");
                sb.Append("</div>");
                sb.Append("<div class=\"cnt-row-act\">");
                sb.Append("<button class=\"cnt-mini\" type=\"button\" onclick=\"ContactJs.edit('"
                          + JsEscape(id) + "','" + JsEscape(name) + "','" + JsEscape(email)
                          + "')\">{!Edit!}</button>");
                sb.Append("<button class=\"cnt-mini cnt-mini-del\" type=\"button\" onclick=\"ContactJs.askDelete('"
                          + JsEscape(id) + "')\">{!Remove!}</button>");
                sb.Append("</div></div>");
            }
            return sb.ToString();
        }

        private static string JsEscape(string s)
        {
            return (s ?? string.Empty).Replace("\\", "\\\\").Replace("'", "\\'")
                                      .Replace("\r", " ").Replace("\n", " ");
        }
    }

scripts/Contact.js
var ContactJs = (function () {

    var TXT = null;
    function t(k) {
        if (!TXT) { TXT = $GetVarData('ContactText'); }
        return (TXT && TXT[k]) ? TXT[k] : '';
    }

    function val(id)  { var e = document.getElementById(id); return e ? e.value : ''; }
    function set(id, v) { var e = document.getElementById(id); if (e) e.value = v; }
    function show(id) { var e = document.getElementById(id); if (e) e.style.display = ''; }
    function hide(id) { var e = document.getElementById(id); if (e) e.style.display = 'none'; }
    function txt(id, s) { var e = document.getElementById(id); if (e) e.textContent = s; }
    function showModal(id) { var e = document.getElementById(id); if (e) e.style.display = 'flex'; }

    function busy(on) {
        var b = document.getElementById('cnt-save');
        var l = document.getElementById('cnt-save-label');
        if (b) b.disabled = on;
        if (l) l.textContent = on ? t('saving') : t('btn_save');
    }

    // ── actions ─────────────────────────────────────────────
    function save() {
        hide('cnt-err'); hide('cnt-ok');

        var name = val('cnt-name').trim();
        if (!name) { onError('err_name'); return; }

        var email = val('cnt-email').trim();
        if (email && (email.indexOf('@') < 0 || email.indexOf('.') < 0)) { onError('err_email'); return; }

        busy(true);
        $WaitOn();
        $ApiRequest('Save', null);   // the form travels in the envelope
    }

    function edit(id, name, email) {
        set('cnt-id', id); set('cnt-name', name); set('cnt-email', email);
        hide('cnt-err'); hide('cnt-ok');
        var f = document.getElementById('cnt-name');
        if (f) f.focus();
    }

    function clear() {
        set('cnt-id', ''); set('cnt-name', ''); set('cnt-email', '');
        hide('cnt-err'); hide('cnt-ok');
    }

    function askDelete(id) {
        set('cnt-delid', id);
        txt('cnt-confirm-msg', t('ask_delete'));
        showModal('cnt-confirm');
    }

    function closeConfirm() { hide('cnt-confirm'); }

    function confirmDelete() {
        hide('cnt-confirm');
        $WaitOn();
        $ApiRequest('Delete', JSON.stringify([
            { key: 'contactid', vlu: val('cnt-delid') }
        ]));
    }

    // ── server callbacks ────────────────────────────────────
    function onError(key) {
        busy(false);
        hide('cnt-ok');
        txt('cnt-err-msg', t(key) || t('err_generic'));
        show('cnt-err');
    }

    function onSaved() {
        busy(false);
        hide('cnt-err');
        txt('cnt-ok-msg', t('ok_saved'));
        show('cnt-ok');
        clear();
    }

    function onDeleted() {
        hide('cnt-err');
        txt('cnt-ok-msg', t('ok_deleted'));
        show('cnt-ok');
    }

    function reveal() {
        var f = document.getElementById('cnt-name');
        if (f) setTimeout(function () { f.focus(); }, 200);
    }

    return {
        reveal:        function ()          { reveal(); },
        save:          function ()          { save(); },
        edit:          function (i, n, e)   { edit(i, n, e); },
        clear:         function ()          { clear(); },
        askDelete:     function (i)         { askDelete(i); },
        closeConfirm:  function ()          { closeConfirm(); },
        confirmDelete: function ()          { confirmDelete(); },
        onError:       function (k)         { onError(k); },
        onSaved:       function ()          { onSaved(); },
        onDeleted:     function ()          { onDeleted(); }
    };

})();

The round trips, annotated

GET /Contact

  1. Constructor: Translation = true, dictionary loaded for target Contact.
  2. OnInit (in WebBase) checks the session.
  3. OnInitialized reads the rows, builds the fragment, replaces {plhd_rows}, queues ContactText.
  4. Render: skynet.core.js, Contact.css, Contact.js injected.
  5. OnAfterRender: every {!…!} in the document is resolved.
  6. Document arrives → Contact.js evaluates → InitialScripts run → $VarData.ContactText populated.

Clicking Save

  1. ContactJs.save() validates locally, disables the button, raises the spinner.
  2. $ApiRequest('Save', null) — no payload at all. The envelope already carries contactid, cnt-name and cnt-email.
  3. Server: GetDataValue reads them, validates again, inserts or updates.
  4. Response: SetElementContents("cnt-rows", …) then ExecuteScript("ContactJs.onSaved();") — in that order.
  5. TranslateApiResponse resolves any tokens in the fragment.
  6. Client: the list is replaced, then onSaved re-enables the button, shows the message and clears the form.

Clicking Remove

  1. askDelete(id) stores the id in a hidden field and opens the page-local modal with display:flex.
  2. confirmDelete() sends the id explicitly — it is action-specific, not form state.
  3. Server deletes with both CONTACT_ID and USER_ID in the WHERE clause.
  4. Same response shape: rows replaced, then callback.

Why validate on both sides. The client check gives an instant response and saves a round trip. The server check is the one that actually protects the database — the client can be bypassed entirely. Neither replaces the other, and the messages should come from the same ContactText keys so they cannot drift apart.

Review questions

Before a page is done, five questions catch most of what the automated checks cannot:

  1. Is every SQL value a parameter, and is every query scoped by owner?
  2. Is every value spliced into markup encoded, and every value in a script string escaped?
  3. Does every error path leave the UI usable — button re-enabled, spinner cleared, message shown?
  4. Is there a user-visible string literal anywhere in the .js? If so it can never be translated.
  5. Does the page work when the data is empty, when the session has expired, and when the write fails?

Briefing an assistant

A short standing brief covers most of what goes wrong. Something like:

SkyNet page, four files: Page.cs / Page.html / Page.js / Page.css. Self-contained — duplicate rather than share; no helpers across pages. CSS prefix pfx-, JS namespace PageJs as one IIFE, page-local DTOs. Server returns ApiResponse ops; never return data for the client to render.
